# 服务化方案（Python 优先；基于当前 CLI/skills 文档）

> 目标：把“依赖 CLI 的 insight/analyzer/report 流程”服务化，用户通过客户端/网页提交任务；服务端具备内网访问权限，调用 `http://172.17.129.204:6829` 获取 DNA/DAA 数据；采用异步任务；最终用户拿到 **数据洞察分析 summary** + **HTML 报告**。
>
> 说明：以下为“方案设计”，会基于现有文档中已确认的接口与流程做映射；对文档未给出的部分会标注“未确认/建议”。

## 1) 现状到服务化的映射（基于现有文件）

现有三段式流程（insight → analyzer → report）对应服务端 Job 的三个阶段：

- **阶段 A：拉取数据（insight）**：调用内网 API 创建任务/轮询状态/拿到 `oss_url` 下载结果文件
- **阶段 B：分析（analyzer）**：对 Excel 进行多发/碰撞/风险检测，产出分析结果与 summary
- **阶段 C：出报告（report）**：把 summary/关键发现渲染成 HTML

**证据（现状流程）**
- 三 skill 与典型流程：`xuqiu/README.md:3-10`
- 内网 API 与异步：`xuqiu/gemini/insight/SKILL.md:27-136`、`xuqiu/gemini/insight/SKILL.md:142-143`
- analyzer 二进制与参数：`xuqiu/gemini/analyzer/SKILL.md:12-58`
- report 输出 HTML 要求：`xuqiu/gemini/report/SKILL.md:8`

## 2) 总体架构（建议）

### 2.1 组件划分

- **API 服务（Python/FastAPI）**：对外提供 `/jobs` 等 REST 接口；只负责鉴权、入参校验、落库、入队。
- **异步任务执行器（Python Worker）**：从队列取任务，执行“调用内网 API → 下载 → 分析 → 生成报告”，并把产物写入存储。
- **元数据存储（建议 PostgreSQL/SQLite 起步）**：保存 Job 状态、参数、审计信息、产物引用（路径/URL）。
- **文件/产物存储（建议统一）**：
  - 起步：本地磁盘（按 job 隔离目录）
  - 规模化：MinIO/S3（存 input/data/analysis/report）
- **前端（可选）**：最小可用可先只做 API；后续补 Web UI（上传、进度、预览 HTML、下载文件）。

### 2.2 Job 状态机（建议）

`created → upstream_created → upstream_running → data_ready → analyzing → report_ready → success`  
失败：任一阶段 `failed`（记录 `error_code/error_message`）；支持 `canceled`。

> 现状存在 `pending/running/success/failed`（内网 API 的任务状态）。服务端 Job 可在此之上加更细粒度阶段。
>
> 证据：`xuqiu/README.md:340-348`

## 3) API 设计（对外服务端）

以下是建议的最小 API 集合；返回字段以“可追踪 + 可下载 + 可审计”为目标。

### 3.1 创建任务：`POST /jobs`

**请求（multipart/form-data）**
- `file`：用户上传的 CSV/Excel（必须包含 `cdid` 列）
- `name`：任务名（可选；为空则服务端生成）
- `package_name`：包名（必填；与内网 API 一致）
- `start` / `end`：日期范围 `YYYY-MM-DD`（建议必填；与内网 API 参数表一致）
- `message`：数组/多值（`dna`/`daa`，可多选；与内网 API 一致）

**响应（JSON 示例）**
```json
{
  "job_id": "job_01HXYZ...",
  "status": "created",
  "created_at": "2026-01-23T17:00:00Z",
  "params": {
    "name": "波克问题数据分析-12-12_v1",
    "package_name": "com.saiyun.drbyqp",
    "time_range": ["2025-12-01", "2025-12-17"],
    "message": ["dna", "daa"]
  }
}
```

**与现状/内网 API 的对齐证据**
- 内网 create 接口与字段：`xuqiu/gemini/insight/SKILL.md:27-44`
- 支持多 `message`：`xuqiu/gemini/insight/SKILL.md:43-44`、`xuqiu/gemini/insight/SKILL.md:45-53`
- 输入文件必须包含 `cdid`：`xuqiu/README.md:293-310`
- demo 示例参数：`xuqiu/demo/demo.md:1-8`（用户名路径已遮蔽）

> 未确认：内网 `/task/create` 的 `start/end` 是否真正必填（参数表写必填但示例缺失）。建议服务端以“必填”做约束，同时在对接期通过一次真实调用确认。  
> 证据：`xuqiu/gemini/insight/SKILL.md:35-44` vs `xuqiu/gemini/insight/SKILL.md:45-53`

### 3.2 查询任务：`GET /jobs/{job_id}`

**响应（JSON 示例）**
```json
{
  "job_id": "job_01HXYZ...",
  "status": "analyzing",
  "upstream": {
    "base_url": "http://172.17.129.204:6829",
    "task_id": "1234567890",
    "task_status": "success"
  },
  "progress": {
    "stage": "analyzing",
    "percent": 70
  },
  "artifacts": {
    "data": "/jobs/job_01HXYZ.../data",
    "report": "/jobs/job_01HXYZ.../report"
  },
  "timestamps": {
    "created_at": "2026-01-23T17:00:00Z",
    "updated_at": "2026-01-23T17:10:00Z"
  }
}
```

### 3.3 下载数据文件：`GET /jobs/{job_id}/data`

- 返回：`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`（或打包 zip，包含原始上传文件 + 下载的详情文件）
- 建议支持：`?download=1`（触发浏览器下载）

> 证据（内网 API 的 `oss_url` 指向结果文件）：`xuqiu/gemini/insight/SKILL.md:118-136`

### 3.4 获取报告：`GET /jobs/{job_id}/report`

两种实现都可（按前端/客户端需要二选一）：

- **方案 1：直接返回 HTML**（`Content-Type: text/html; charset=utf-8`）
- **方案 2：返回 JSON（含预览 URL / 下载 URL）**

**现状证据（HTML 报告要求）**
- `xuqiu/gemini/report/SKILL.md:8`
- `xuqiu/README.md:439-483`

### 3.5 可选：取消任务 `POST /jobs/{job_id}/cancel`

- 作用：停止轮询/停止后续分析（内网 task 是否可取消未在文档中给出，需补充）

## 4) 服务端如何对接内网 API（基于已知接口）

### 4.1 已确认的内网接口（来自 insight skill）

1) 创建任务：`POST /api/statistical-analysis/v1/task/create`（multipart/form-data）  
2) 查询列表：`POST /api/statistical-analysis/v1/task/list`（JSON）  
3) 查询详情：`GET /api/statistical-analysis/v1/task/detail?task_id=xxx`（返回 `status`、`oss_url` 等）  

**证据**

### 4.2 Worker 执行逻辑（建议）

1) 保存上传文件到 job 工作目录（只读留档，便于审计/复现）

4) 当 `status=success` 且拿到 `oss_url` 后下载 Excel 到存储  
5) 进入分析与报告阶段

## 5) 分析与报告生成（尽量单一技术栈）

### 5.1 分析（summary + 结构化结果）

现状 analyzer 是本地二进制工具（未在本次目录提供）。服务化有两条落地路径：

- **路径 A（短期迁移，最小改造）**：服务端部署/打包 analyzer 可执行文件，通过 subprocess 调用，复用现有输出（Excel 多 Sheet）。
  - 证据：`xuqiu/gemini/analyzer/SKILL.md:12-47`、`xuqiu/README.md:416-435`
- **路径 B（中期统一技术栈）**：用 Python 复刻/重写检测逻辑，直接输出结构化 JSON + 可选 Excel（用 openpyxl/xlsxwriter）。
  - 未确认：检测算法细节与阈值（当前文档只描述类型与 Sheet 名），需要补充（见第 8 节风险）。

建议无论 A/B，都产出统一的 **summary JSON**（供报告、前端展示、审计用），例如：
```json
{
  "duplicate": {"groups": 15, "rows": 120},
  "impact": {"groups": 8, "rows": 60},
  "risk": {"rows": 3, "top_rules": [{"rule": "rc_xxx", "count": 2}]}
}
```

### 5.2 报告（HTML）

优先建议 **模板化生成（Jinja2）**，把 summary/图表数据（ECharts/Plotly）渲染成 HTML；必要时再用模型生成“文字解读”部分，但只提供聚合后的 summary，避免把全量数据喂给模型。

**现状证据（报告期望：专业 + 图表 + 颜色强调 + HTML）**
- `xuqiu/gemini/report/SKILL.md:8`
- `xuqiu/README.md:443-475`

## 6) 权限与审计（内网场景最低要求，建议）

> 现有文档未给出任何鉴权方式；以下为服务化建议，需结合你们内网现状落地（未确认）。

### 6.1 鉴权建议（按优先级）

1) **内网网关统一鉴权**（SSO/OIDC → JWT），服务端只验签与 RBAC  
2) **mTLS（客户端证书）**（适合机器到机器）  
3) **API Key（短期）**：绑定用户/系统 + 过期 + 权限范围

### 6.2 审计日志建议记录字段

- `who`：用户/应用标识、来源 IP、UA、认证主体  
- `what`：job_id、入参摘要（包名、日期范围、message 类型）、上传文件名/大小/哈希（不记录文件内容）  
- `upstream`：内网 task_id、请求 URL（不含敏感 query）、响应 code、耗时、重试次数  
- `artifacts`：生成的文件列表、大小、哈希、下载次数  
- `errors`：错误码、错误摘要（避免写入 cdid/imei 等敏感字段）  

### 6.3 敏感信息处理

- 日志/报告中对 `cdid/imei/android_id` 等字段默认脱敏（只显示前后 3~4 位）  
- 产物存储设置生命周期（例如 7/30/90 天自动清理）  
- 传输层 HTTPS（即便内网）+ 存储加密（如磁盘加密/对象存储 SSE）

**现状证据（字段敏感性）**
- 输出包含 `imei/android_id` 等：`xuqiu/README.md:351-363`

## 7) 性能与扩展性（建议）

### 7.1 大数据不直接喂给模型

- 分析阶段先生成 summary（计数、分组、TOP N、分布、抽样），模型只读 summary  
- 对大文件采取分块读取/流式处理；必要时先落地为 Parquet 以便二次分析  

### 7.2 并发与资源隔离

- Worker 侧限制并发（按 CPU/内存），每个 job 独立工作目录  
- 对外 API 限流（按用户/Key）  
- 长任务设置超时与最大重试；对内网 API 做指数退避与熔断（避免雪崩）

## 9) 风险清单与备选方案（结合现状）

1) **内网 API 不稳定/慢/失败**：必须做超时、重试、限流、熔断；Job 支持断点续跑（保存 upstream_task_id）。

2) **`start/end` 等字段不确定导致对接反复**：先用一组真实请求确认契约，再固化到服务端校验层。
   - 现状证据：参数表与示例不一致：`xuqiu/gemini/insight/SKILL.md:35-53`
