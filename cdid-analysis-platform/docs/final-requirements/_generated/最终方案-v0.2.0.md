## 1. 目标与范围

### 1.1 MVP 目标

- 将现有 Gemini CLI 的“数据获取→分析→报告”流程包装为 Web 服务：用户在浏览器完成上传、参数选择、查看结果。
- 任务全流程自动化：上传 → 调用内网 API 获取 Excel → Python 脚本分析 → Gemini CLI 生成 HTML 报告。
- 可追溯与可运维：任务有状态机、进度、错误信息，可重试，可下载原始数据与报告。
- 可扩展：通过“管线（Pipeline）”机制新增分析脚本与报告能力。

### 1.2 MVP 非目标（先不做/可后续）

- 与现有权限系统深度集成（先屏蔽/弱化登录鉴权，后期再对接）。
- 并发队列/多 Worker 并行（MVP 单线程 FIFO）。
- 完整监控告警/审计日志（后期补）。
- 在 Web UI 中“新建 Skill/扩展”（仅引用现成能力，安装/导入走人工/运维流程）。

## 2. 已确认关键决策（最终结论）

1. **管线定义**：`Pipeline = Python 分析脚本（analyzer.py） + Gemini CLI 调用能力（@skill_name）`；一个任务只跑一条管线。
2. **内网 API**：Base URL `http://172.17.129.204:6829`；创建任务接口 `start/end` **必填**（`YYYY-MM-DD`）；`message` 可选，多选通过 multipart **重复字段**传递（`message=dna`、`message=daa`）。
3. **Gemini CLI 调用方式**：使用 Headless 一次性调用，**stdin 传入 JSON**，prompt 里用 `@skill_name` 触发能力；`-s` 不是 skill 参数（是 sandbox），不使用。
4. **脚本命名/组织**：脚本文件名固定 `analyzer.py`，通过目录区分不同分析逻辑/版本。
5. **任务规模与执行策略**：典型 CDID 数量 100-1000；MVP 单任务串行；内网任务典型耗时 5-30 分钟。
6. **数据分析口径（MVP）**：
   - 多发检测：按设备标识去重后关联多个 cdid 即命中（先做最简单可运行口径，后续增强规则）。
   - 碰撞检测：**相同 DID，不同设备型号** 为碰撞。
   - 风险检测：与“风险表/异常口径”一致（规则表未给出时，先做可配置规则 + 兜底口径）。

## 3. 端到端流程（MVP）

```
用户（Web UI）
  选择客户（自动填充包名）+ 上传 CDID.csv + 选择管线 + 选择 start/end + 选择 message_types(dna/daa)
        |
        v
API Server（FastAPI）
  保存上传文件 jobs/{job_id}/input.csv
  写 jobs 表：status=queued
        |
        v
Worker（FIFO 单线程）
  fetching:
    - 调用内网 API 创建任务（start/end 必填）
    - message_types(dna/daa) 以 multipart 重复字段传递（message 可不传）
    - 轮询查询状态（建议 60s 间隔；超时可配置，建议默认 >= 60min）
    - 成功后下载 Excel -> jobs/{job_id}/raw_data.xlsx
  analyzing:
    - 动态导入 {script_dir}/analyzer.py
    - analyze(raw_data.xlsx, user_info, start_date, end_date) -> dict
    - 保存 jobs/{job_id}/analysis_result.json
  reporting:
    - cat analysis_result.json | gemini "@<skill_name> ...生成HTML..."
    - 保存 jobs/{job_id}/report.html
  done/failed:
    - 更新状态、进度、错误信息；failed 支持 retry
        |
        v
用户查看
  GET /jobs/{id}/report 展示报告
  GET /jobs/{id}/raw-data 下载原始 Excel
```

## 4. Gemini CLI 调用规范（关键落地项）

### 4.1 约定

- Worker 调用 Gemini CLI 时，建议将工作目录设置为 `jobs/{job_id}/`（方便 Skill/扩展如需读写文件，也能落在任务目录）。
- 输出以 **stdout 返回 HTML** 为主，由 Worker 写入 `report.html`。

### 4.2 推荐命令模板

```bash
cat analysis_result.json | gemini "@<skill_name> 请根据以上JSON生成完整HTML报告，只输出HTML代码（包含<html><head><body>）"
```

说明：
- `@<skill_name>`：来自管线配置；按实际 CLI 能力（扩展/skill）命名。
- 若现网仍沿用 `-p`，也可使用 `gemini -p "..."`（但该 flag 在 CLI 帮助中标注为 deprecated）。

### 4.3 Skill/扩展管理边界

- Skill/扩展的安装/导入/更新由管理员在 Gemini CLI 环境中完成（平台不负责复制目录、不负责新建）。
- 平台只需要：
  - 在管线配置中保存 `skill_name`；
  - 调用时把 `@skill_name` 拼进 prompt；
  - 失败时记录 stderr 以便排查（缺能力/权限/配额/格式等）。

## 5. 数据分析逻辑（MVP 口径）

### 5.1 输入数据约定（raw_data.xlsx）

最低假设：Excel 至少包含 `cdid`，以及用于检测的若干字段（如 `did/oaid/android_id/imei/device_model/rc_rules/rc_scenes`）。

为避免“字段名不一致”阻塞落地，建议在脚本层做一层 **字段映射/容错**：
- 必填：`cdid`
- 可选：`did`, `oaid`, `android_id`, `imei`, `device_model`, `rc_rules`, `rc_scenes`

### 5.2 多发检测（duplicate）

**MVP 口径**：对设备标识去重后，若同一标识关联的唯一 `cdid` 数量 > 1，则命中多发。

建议实现策略（可扩展）：
- 优先基于 `did`（如缺失可用 `oaid/android_id/imei` 兜底）分别分组；
- 输出结果携带：命中类型（did/oaid/android_id/imei）、标识值、cdid 列表、数量。

### 5.3 碰撞检测（impact）

**口径（已确认）**：相同 `did`，出现多个不同 `device_model`（或设备型号字段）即命中碰撞。

输出建议：
- did
- device_models（去重列表）
- cdid_list（去重列表）

### 5.4 风险检测（risk）

**目标口径**：与“风险表/异常口径”一致。

**MVP 方案**（确保可落地）：
- 风险规则做成可配置（例如 YAML/JSON：`risk_rules`/`risk_scenes` 的枚举或正则列表）。
- 在规则未补齐前，提供兜底：`rc_rules` 或 `rc_scenes` 非空即标记为风险（并在报告中明确“兜底规则”）。

### 5.5 输出 JSON（analysis_result.json）

- 必须是可 JSON 序列化 dict
- 需包含 summary 与各模块结果数组（duplicate/impact/risk）

## 6. 存储与 API（MVP 不变）

- 数据库表：`jobs` / `pipelines` / `clients` / `users`（见 `方案设计-v0.2.0.md` 的表结构）
- 核心 API：
  - `POST /jobs` 创建任务
  - `GET /jobs` / `GET /jobs/{id}` 查询
  - `GET /jobs/{id}/report` 报告
  - `GET /jobs/{id}/raw-data` 原始 Excel
  - `POST /jobs/{id}/retry` 重试失败任务
